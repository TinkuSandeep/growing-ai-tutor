BATCH DASHBOARD - PARTIAL JOB UPDATE TROUBLESHOOTING
=====================================================

Problem
-------
Some AutoSys jobs receive job_status, job_start_time and job_end_time, while other rows remain NULL.

Important
---------
The ingestion program updates existing catalog rows. It does not insert new job catalog rows.

Current evidence indicates that AutoSys/AEWS collection is completing, but the database update stored procedure is not matching every target row. The current target_rows_updated value counts stored-procedure calls and does not confirm how many database rows were actually updated.


STEP 1 - SELECT ONE WORKING AND ONE FAILING JOB
------------------------------------------------

Run:

SELECT
    job_name,
    scheduler_instance,
    job_start_time,
    job_end_time,
    job_status,
    last_updated_date
FROM dbo.cp_critical_batch_jobs
ORDER BY last_updated_date DESC;

Select:

1. One working job with job_status = 'SU'.
2. One failing job where job_status, job_start_time and job_end_time remain NULL.

Copy the exact job_name and scheduler_instance for both jobs.


STEP 2 - CONFIRM DISCOVERY RETURNS BOTH JOBS
---------------------------------------------

EXEC dbo.cp_Get_Critical_Batch_Jobs;

Confirm that both jobs are returned. Check:

- job_name
- scheduler_instance
- Correct instance: PB3, PC3 or PG3
- No unexpected leading or trailing spaces

If the missing job is not returned, investigate dbo.cp_Get_Critical_Batch_Jobs. Python cannot update a job that was not discovered.


STEP 3 - CHECK SPACES AND INSTANCE VALUES
------------------------------------------

Replace WORKING_JOB_NAME and FAILING_JOB_NAME below:

SELECT
    job_name,
    scheduler_instance,
    '[' + job_name + ']' AS visible_job_name,
    '[' + scheduler_instance + ']' AS visible_instance,
    LEN(job_name) AS name_characters,
    DATALENGTH(job_name) AS name_bytes,
    LEN(scheduler_instance) AS instance_characters,
    job_status,
    job_start_time,
    job_end_time
FROM dbo.cp_critical_batch_jobs
WHERE LTRIM(RTRIM(job_name)) IN
(
    N'WORKING_JOB_NAME',
    N'FAILING_JOB_NAME'
);

Look for:

- Leading or trailing spaces
- PB3 versus pb3
- Incorrect scheduler instance
- Different punctuation in the job name
- Unexpected characters


STEP 4 - CHECK DUPLICATE JOB NAMES
-----------------------------------

SELECT
    LTRIM(RTRIM(job_name)) AS normalized_job_name,
    COUNT(*) AS row_count,
    STRING_AGG(scheduler_instance, ', ') AS instances
FROM dbo.cp_critical_batch_jobs
GROUP BY LTRIM(RTRIM(job_name))
HAVING COUNT(*) > 1;

If this returns rows, job_name alone cannot uniquely identify a record.

The update key must be:

    job_name + scheduler_instance


STEP 5 - VERIFY THE AUTOSYS RESULT BEFORE DATABASE WRITE
--------------------------------------------------------

Run locally without --write:

    python -m autosys_phase1.source_check --settings config/settings.yaml

Find the failing job in the output. Confirm that it contains:

- Correct job_name
- Correct scheduler_instance
- job_status such as SU
- Non-NULL job_start_time
- Non-NULL job_end_time for a completed job

Interpretation:

- If the values are missing here, investigate the AEWS response or transformation.
- If the values are present here but missing in SQL Server, investigate the database stored procedure and its matching conditions.


STEP 6 - CHECK UPDATE PROCEDURE PARAMETERS
-------------------------------------------

SELECT
    p.parameter_id,
    p.name AS parameter_name,
    TYPE_NAME(p.user_type_id) AS data_type,
    p.max_length
FROM sys.parameters AS p
WHERE p.object_id = OBJECT_ID(N'dbo.cp_Update_Job_Execution_Status')
ORDER BY p.parameter_id;

The procedure should have these five parameters:

1. @job_name
2. @scheduler_instance
3. @job_start_time
4. @job_end_time
5. @job_status

If @scheduler_instance is missing, the procedure is using the old four-parameter contract.


STEP 7 - INSPECT THE UPDATE PROCEDURE
--------------------------------------

EXEC sys.sp_helptext N'dbo.cp_Update_Job_Execution_Status';

The WHERE clause should match both fields:

WHERE LTRIM(RTRIM(job_name)) = LTRIM(RTRIM(@job_name))
  AND UPPER(LTRIM(RTRIM(scheduler_instance))) =
      UPPER(LTRIM(RTRIM(@scheduler_instance)));

Also check for additional conditions such as:

- is_active
- job_type
- business_date
- scheduler name
- application name

An incorrect additional condition can prevent only certain jobs from being updated.


STEP 8 - TEST ONE FAILING JOB SAFELY
-------------------------------------

Use the actual job name, scheduler instance and timestamps returned by AutoSys.

BEGIN TRANSACTION;

EXEC dbo.cp_Update_Job_Execution_Status
    @job_name = N'FAILING_JOB_NAME',
    @scheduler_instance = N'PB3',
    @job_start_time = '2026-10-13T07:30:00',
    @job_end_time = '2026-10-13T07:35:00',
    @job_status = 'SU';

SELECT
    job_name,
    scheduler_instance,
    job_start_time,
    job_end_time,
    job_status,
    last_updated_date
FROM dbo.cp_critical_batch_jobs
WHERE LTRIM(RTRIM(job_name)) = N'FAILING_JOB_NAME'
  AND UPPER(LTRIM(RTRIM(scheduler_instance))) = N'PB3';

ROLLBACK TRANSACTION;

Interpretation:

- One row changes inside the transaction: verify Python's stored-procedure parameters.
- No row changes: the procedure's matching logic is incorrect.
- Multiple rows change: the procedure does not use a unique key.
- The procedure rejects @scheduler_instance: SQL and Python are still using the old four-parameter contract.

ROLLBACK makes this test non-permanent.


STEP 9 - CHECK THE PYTHON DATABASE CALL
----------------------------------------

Open:

    src/autosys_phase1/database.py

The procedure call should pass five parameters:

sql = f"""
    EXEC {settings.quoted_update_stored_procedure}
        @job_name = ?,
        @scheduler_instance = ?,
        @job_start_time = ?,
        @job_end_time = ?,
        @job_status = ?
"""

parameters = (
    update.target.job_name,
    update.target.instance,
    _to_sql_datetime(update.job_start_time),
    _to_sql_datetime(update.job_end_time),
    update.job_status,
)

Verify that SQL Server and Python use the same parameter names, number and order.


STEP 10 - MAKE ZERO-ROW UPDATES FAIL
-------------------------------------

The stored procedure should confirm that exactly one row was updated:

DECLARE @rows_updated INT;

UPDATE dbo.cp_critical_batch_jobs
SET
    job_start_time = @job_start_time,
    job_end_time = @job_end_time,
    job_status = @job_status,
    last_updated_date = SYSDATETIME()
WHERE LTRIM(RTRIM(job_name)) = LTRIM(RTRIM(@job_name))
  AND UPPER(LTRIM(RTRIM(scheduler_instance))) =
      UPPER(LTRIM(RTRIM(@scheduler_instance)));

SET @rows_updated = @@ROWCOUNT;

IF @rows_updated <> 1
BEGIN
    THROW 50001,
          'Job runtime update must match exactly one database row',
          1;
END;

SELECT @rows_updated AS rows_updated;

This prevents false success when the procedure matched zero rows.


STEP 11 - RUN THE LOCAL UPDATE
-------------------------------

After Python and SQL use the same five-parameter contract, run:

    python -m autosys_phase1.source_check --settings config/settings.yaml --write


STEP 12 - VERIFY THE FINAL RESULT
----------------------------------

SELECT
    COUNT(*) AS total_jobs,
    SUM(CASE WHEN job_status IS NOT NULL THEN 1 ELSE 0 END)
        AS jobs_with_status,
    SUM(CASE WHEN job_status IS NULL THEN 1 ELSE 0 END)
        AS jobs_without_status,
    SUM(
        CASE
            WHEN job_status IN ('SU', 'FA', 'TE')
             AND (job_start_time IS NULL OR job_end_time IS NULL)
            THEN 1
            ELSE 0
        END
    ) AS invalid_terminal_jobs
FROM dbo.cp_critical_batch_jobs;

List remaining problem jobs:

SELECT
    job_name,
    scheduler_instance,
    job_start_time,
    job_end_time,
    job_status,
    last_updated_date
FROM dbo.cp_critical_batch_jobs
WHERE job_status IS NULL
   OR (
        job_status IN ('SU', 'FA', 'TE')
        AND (job_start_time IS NULL OR job_end_time IS NULL)
      )
ORDER BY scheduler_instance, job_name;


MOST LIKELY ROOT CAUSE
----------------------

Discovery identifies a job using job_name and scheduler_instance, but the current update procedure/Python call appears to use only job_name. Some rows therefore match and update, while other rows remain NULL.

The target_rows_updated value must also be changed to report confirmed database rows instead of the number of stored-procedure calls.
